## 1. 项目背景

企业知识散落在 PDF、DOCX、PPT、Markdown 等各类文档中，检索依赖人工或传统关键词搜索，效率低且难以回答跨文档、多步骤的复杂问题。本项目构建一套**企业级 RAG Agent**：

- 支持多格式、多文档的企业知识库；
- 具备混合检索、精排、引用溯源的能力，回答可追溯、可采信；
- 通过 Agent 编排支持复杂多跳问答、查询改写、自我反思（CRAG）；
- 提供完整的评估体系、可观测性与权限隔离，达到企业内部生产可用标准。

## 2. 项目目标与非目标

### 2.1 目标

| 编号 | 目标 |
|---|---|
| G1 | 端到端支持「上传文档 → 解析索引 → 自然语言问答 → 带引用溯源的回答」 |
| G2 | 中文为主的中长文档（10~500 页）问答质量达到内部可用标准（见 §7 验收标准） |
| G3 | 支持万级文档、百万级文本分块（chunk）的检索规模 |
| G4 | 回答必须附引用来源，支持跳转原文；不允许无依据编造 |
| G5 | 权限隔离：不同角色/租户只能检索到其有权访问的文档 |
| G6 | 建立评估与回归体系，任何改动可量化验证、可回滚 |

### 2.2 非目标（本期不做）

- 不做大模型训练 / 微调 / 领域基座模型；
- 不做通用对话助手（非知识库问题可礼貌拒答）；
- 不做知识图谱自动构建（GraphRAG 列入 P2 备选，不阻塞主线）；
- 不做移动端/桌面客户端（以 Web 端 + API 为主）；
- 不做多模态文档问答（图表问答列入远期规划）。

## 3. 用户角色与典型场景

| 角色 | 说明 | 核心诉求 |
|---|---|---|
| 业务用户 | 使用知识库问答的普通员工 | 快速准确得到答案、引用可核实、支持追问 |
| 知识库管理员 | 上传/管理文档、维护权限 | 批量导入、增量更新、权限配置、质量监控 |
| 开发/运维 | 部署、调优、排障 | 可观测性、评估指标、日志与 trace |
| 系统对接方 | 通过 API 集成到其他系统 | 稳定的 OpenAPI、流式输出、结构化响应 |

典型场景：

- S1 单文档问答：对一份产品手册提问，回答引用该手册章节；
- S2 跨文档多跳问答：如「A 产品的部署要求与 B 产品的兼容性说明」，需跨多份文档检索并推理；
- S3 权限隔离查询：不同部门用户查询同一知识库，只能看到本部门文档内容；
- S4 文档更新：文档 V2 上传后，V1 内容立即失效，问答不再引用；
- S5 质量回归：检索/分块策略调整后，跑黄金数据集验证指标不劣化。

## 5. 非功能需求

| 类别 | 指标 |
|---|---|
| 性能 | 首 token 延迟 P95 ≤ 2s（中等负载）；单次完整回答 P95 ≤ 15s |
| 性能 | 检索（混合检索+重排）P95 ≤ 800ms；万级文档、百万 chunk 规模下不劣化 |
| 性能 | 文档解析吞吐：≥ 10 页/秒/worker（PDF 文本型） |
| 并发 | 支持 ≥ 50 并发问答会话 |
| 可用性 | 服务可用性 ≥ 99.5%；摄入失败不影响问答服务 |
| 扩展性 | 摄入 worker、API 服务可水平扩展；向量库支持分片 |
| 安全 | 认证鉴权全覆盖；权限过滤在检索层执行；传输加密；敏感配置不入库 |
| 数据 | 知识库数据可备份/恢复；删除文档 24h 内从所有缓存生效 |
| 兼容 | 服务端部署于 Linux（Docker）；开发环境支持 Windows |
| 成本 | 单机起步可运行全部组件（内存 ≥ 16G）；LLM 可切换本地/云端 API |

## 7. 验收标准

P0 验收（自动化 + 人工）：

1. 端到端流程：上传 3 种以上格式样例文档（PDF 复杂版式、DOCX、Markdown），问答回答正确并带可跳转引用；
2. 黄金数据集评估：faithfulness ≥ 0.85，answer relevance ≥ 0.80（以所选模型基线为准，数值待首次评估后校准）；
3. 拒答能力：对知识库外问题不编造，明确提示无依据；
4. 权限隔离：低权限账号检索不到高权限文档内容（含关键词直接提问验证）；
5. 文档更新：V2 上传后，针对旧内容的提问不再引用 V1；
6. 可靠性：摄入任务失败可重试；问答服务在向量库重启期间优雅降级（报错而非崩溃）。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| PDF 复杂版式（表格、多栏、扫描）解析质量差 | 检索召回差、回答错 | 布局感知解析（Docling）+ 人工抽检流程 + 分块可视化；OCR 列入 P1 |
| 中文检索效果不稳定（同义词、术语、口语） | 召回不全 | ✅ 已缓解：BGE-M3 中文模型 + 中文重排 + query 改写（P1）；术语表机制（P2 W5 已落地：config/terms.json 别名映射，term_expand 节点注入检索变体） |
| LLM 幻觉 | 企业采信度低 | 引用溯源强制 + faithfulness 评估 + CRAG 低置信拒答 |
| 权限实现缺陷导致越权 | 严重合规风险 | 过滤下推到向量库 filter；越权测试用例纳入回归 |
| 黄金数据集建设耗时 | 评估体系空转 | 30 条起步（P0 即建），边用边扩；用户反馈回流 |
| 向量库运维成本 | 拖累进度 | P0 用 Docker 单机 Milvus；数据量小时可先本地向量库，接口层抽象屏蔽差异 |
| Python 3.14 生态兼容风险 | 依赖安装失败 | 用 uv 锁定 Python 3.12 虚拟环境 |
| 超长文档（>300 页） | 召回碎片化 | 分层摘要 + MapReduce 总结（P1） |

## 9. 开放问题（需评审确认）

1. LLM 选型：本地开源模型（如 Qwen/DeepSeek 系）还是云端 API？预算与数据合规要求如何？
2. 部署形态：纯内网还是可访问外网（影响 Embedding/重排模型获取方式）？
3. 知识库规模量级预估：首期实际文档数量与年增长？
4. 是否需要多租户（多个独立知识库）还是单知识库 + 权限控制即可？
5. 引用跳转的落地载体：Web 端阅读器预览 PDF 原文，还是渲染解析后的文本？
